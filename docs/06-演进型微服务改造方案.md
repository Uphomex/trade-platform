# 06-演进型微服务改造方案

> 本文回答：如果业务继续增长，如何把当前「单应用 + 清晰包结构」演进为「多服务可独立部署」的系统，并补齐注册配置、网关、事务与可观测性。

## 1. 拆分边界建议

按 **变更频率、团队边界、伸缩瓶颈** 划分第一批服务：

1. **order-service**：下单、订单查询、状态机。  
2. **payment-service**：支付、对账、渠道适配。  
3. **inventory-service**：库存预占、确认、盘点。  
4. **fulfillment-service**：物流下单、轨迹回传。  
5. **bff / gateway**：面向 Web 与 App 的聚合 API（可选）。

单体中已经存在的包名（`order` / `payment` / `inventory` / `fulfillment`）可直接作为拆分时的代码迁移线索。

## 2. 注册与配置：Nacos

- **注册发现**：各服务启动时向 Nacos 注册实例，网关通过服务名做负载均衡。  
- **配置中心**：数据源、MQ Topic、功能开关与 **不同环境**（dev/test/prod）隔离。  
- **迁移策略**：先把「只读配置」迁到 Nacos，再逐步把「会热更新」的参数迁过去；保留本地 `application.yml` 作为默认值兜底。

## 3. API 网关

引入 **Spring Cloud Gateway** 或同类网关：

- 统一 **鉴权**、**限流**、**灰度路由**、**请求日志**。  
- 对外只暴露网关域名，内部服务跑在私有网络。

## 4. 分布式事务：AT vs TCC vs Saga

| 模式 | 特点 | 适用 |
|------|------|------|
| **Seata AT**（当前演示） | 对业务入侵小，依赖数据库 undo_log；性能与隔离级别相关 | 关系型事务边界清晰、能接受 AT 隔离语义 |
| **TCC** | Try / Confirm / Cancel 三阶段，性能与一致性更强，但编码成本高 | 高价值账户、严格资金类 |
| **Saga** | 长事务、逐步补偿，适合跨系统、跨人类审批 | 物流、售后工单流 |

拆分后，「下单 + 预占库存」可能变成跨服务调用：可用 **Seata AT 跨库**、或 **可靠消息最终一致性**（下单后发 MQ，库存服务消费并预占，失败则发补偿消息）。

## 5. 消息驱动与最终一致性

当前仓库已用 RocketMQ 把「支付后履约」异步化。微服务化后建议：

- 所有跨服务写操作尽量 **幂等**（业务键 + 唯一约束）。  
- 重要流程配 **死信队列 DLQ** 与 **人工补偿后台**。  
- 关键消息使用 **事务消息**（若采用 RocketMQ 事务消息模型）或 **Outbox 表**（本地事务与发消息同事务落库）。

## 6. 可观测性（上线必备）

- **日志**：结构化 JSON + traceId，集中采集（ELK / OpenSearch / Loki）。  
- **指标**：Micrometer + Prometheus；关注 QPS、P99、线程池、MQ 堆积、DB 连接池。  
- **链路追踪**：OpenTelemetry + Jaeger/Tempo，把网关 → 各服务 → DB/MQ 串成一条 trace。

## 7. 数据与缓存

- **读写分离**：订单库读副本承载列表查询。  
- **缓存分层**：本地 Caffeine + Redis 集群；注意缓存一致性与击穿防护（见 `04` 文档）。  
- **分库分表**：订单表按用户或时间分片；全局 ID 与路由规则要提前设计。

## 8. 迁移路径（低风险）

1. **双写 / 读切换**：新服务先影子读，对比结果。  
2. **按流量灰度**：1% → 10% → 全量。  
3. **保留单体作为降级预案**：网关层或特性开关一键切回。
