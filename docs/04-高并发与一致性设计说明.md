# 04-高并发与一致性设计说明

> 本文说明「为什么这样做」，即使 v1 仍是单库单应用，也按可扩展思路来讲。

## 1. 防止超卖：数据库乐观锁 vs Redis Lua

### 数据库方案（本项目主路径）

表 `trade_sku` 中：

- `total_stock`：总库存（支付确认后会减少，表示真实出库）。  
- `reserved_stock`：为「未支付订单」预占的数量。  
- `version`：乐观锁版本号。

**预占**、**释放**、**确认** 均通过带 `version` 条件的 `UPDATE`，若影响行数为 0 则重试或失败，从而避免把库存扣成负数。

### Redis + Lua（演示接口）

`FlashSaleRedisService` 使用 **Lua 脚本**在 Redis 中原子判断并 `DECR`，适合「秒杀库存」与极高并发计数场景。注意：Redis 计数与数据库台账之间通常需要 **对账 / 异步同步**，生产环境要谨慎设计，本仓库仅做概念演示。

## 2. 支付回调幂等与防重

### 业务要点

- 网关可能 **重复通知**（网络重试、商户处理超时等）。  
- 必须保证：**多次相同通知与一次通知效果相同**（幂等）。

### 本项目做法

表 `trade_payment_record` 上对 `(biz_type, channel_pay_id)` 建唯一索引。  
支付回调先到账 **插入成功** 再推进订单；若插入冲突（`DuplicateKeyException`），视为已处理过，直接忽略。

## 3. 订单详情缓存与穿透

- **缓存**：`OrderService#getOrderDetail` 将 `OrderDetailResponse` 序列化为 JSON 字符串放入 Redis，TTL 默认 60 秒；订单状态变更时 **删除缓存键**（`evictOrderCache`）。  
- **穿透**：若恶意用大量不存在的 `orderNo` 查询，可能压垮 DB。缓解手段包括：布隆过滤器、短期缓存空结果、接口鉴权与限流。  
- **击穿**：热点 key 过期瞬间并发回源，可用互斥锁或逻辑过期。v1 未展开实现，留作练习。

## 4. 限流

`PaymentCallbackRateLimiter` 对 `/api/payments/callback` 按 IP 做简单计数限流，防止脚本刷接口。

## 5. 分库分表（v1 单库，但设计思路）

当订单表行数达到亿级，常见演进：

- **垂直拆分**：用户库、交易库、报表库分离。  
- **水平分片**：按 `user_id` 或 `order_no` 哈希到多个实例；查询要带分片键，避免广播扫全分片。  
- **全局 ID**：雪花算法、号段、与分片规则对齐。

本仓库用单库降低搭建成本，但在 `06-演进型微服务改造方案.md` 中会与微服务拆分一起串联说明。
